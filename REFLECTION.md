# REFLECTION

## 1. Hardest bug and how you debugged it.
The most challenging technical hurdle encountered during the development of SpendLens AI was a subtle but critical synchronization issue between the client-side `localStorage` state and the server-side hydration in the Next.js App Router environment. Because this application relies heavily on persisting form state so users don't lose their data across refreshes, I initially implemented a naive approach where the state was initialized directly from `localStorage`. This caused a "Hydration Mismatch" error because the server would render the default state (e.g., team size 1), while the client would immediately try to render the saved state (e.g., team size 10).

To debug this, I used the React DevTools to trace the render cycles and realized that the "cascading renders" linting error I was seeing was actually a symptom of this synchronization struggle. I attempted several fixes, including `useLayoutEffect`, but ultimately settled on a robust "isLoaded" pattern. By delaying the rendering of the persisted data until the component had successfully mounted on the client, I was able to ensure that the server-rendered HTML matched the initial client render, effectively silencing the hydration errors. This taught me a great deal about how Next.js handles the boundary between static server generation and dynamic client state, specifically how to manage "side-effect-driven" state initialization in a way that remains performant and doesn't trigger infinite loops of state updates.

## 2. Decision you reversed mid-week.
Around Day 3, I made a significant strategic pivot regarding the core "Audit Logic." My original architectural diagram had the audit engine living behind an AI-powered prompt. I thought it would be "cooler" if an LLM looked at the user's input and "intelligently" suggested savings. However, during early testing, the LLM performed poorly on basic math tasks—it would hallucinate pricing plans that didn't exist or fail to correctly multiply the seat count by the plan price. Even worse, the results were inconsistent; the same input would yield different savings amounts on different runs.

I realized that for a tool focused on financial spending, consistency and accuracy are non-negotiable. If a user sees a "savings" number that they can't verify with a calculator, the entire credibility of the SpendLens AI brand is destroyed. I reversed this decision and decided to build a purely deterministic, rule-based engine in TypeScript. This engine uses hardcoded, verified pricing data and runs through a series of logical "if-then" statements to calculate savings. The AI was then relegated to what it does best: synthesizing that deterministic data into a human-readable, personalized summary. This shift not only improved the speed and reliability of the app but also made the entire system testable with standard unit tests, which was a huge win for long-term maintainability.

## 3. What you would build in week 2.
If I were to continue development into a second week, my primary focus would be on "Automated Data Ingestion." Currently, users have to manually enter their tool spend, which is a significant point of friction. I would build a series of OAuth integrations for the most common AI platforms—OpenAI, Anthropic, and Google Cloud. This would allow a user to simply "Connect OpenAI" and have SpendLens AI automatically fetch their actual usage metrics, token counts, and billing history. This would unlock much deeper insights, such as identifying specific "ghost" API keys that are consuming credits but aren't tied to any active production workloads.

Secondly, I would implement a "Team Workspace" feature. AI spend isn't just an individual problem; it's a cross-functional organizational challenge involving Finance, Engineering, and Operations. By allowing users to create an organization account and invite colleagues, we could provide a unified dashboard that tracks total company-wide AI spend. We could even implement "Spend Alerts" that trigger if the monthly run rate exceeds a certain threshold. Finally, I would build a more robust "Marketplace of Alternatives," where we could suggest specific open-source models (like Llama 3) that could replace expensive proprietary API calls for certain low-complexity tasks, providing an even clearer path to $1,000+/month savings.

## 4. How you used AI tools.
I leveraged AI coding assistants throughout the development lifecycle, but my approach was highly specific: I used them as "Seniors in a specific domain" rather than as a general-purpose copy-paste tool. For the frontend, I used AI to quickly scaffold the complex Tailwind CSS layouts, specifically the glassmorphic cards and the responsive navigation patterns. It was incredibly efficient at translating my high-level design descriptions into functional CSS utility classes, which saved me hours of manual tweaking.

In the backend, I used AI to generate the boilerplate for the Supabase database interactions and the Next.js API routes. Since the requirements for this project involved strict naming conventions and specific data flows, I would feed the AI my `implementation_plan.md` and ask it to "Generate the types and basic CRUD operations for this schema." This allowed me to focus my own cognitive energy on the high-level business logic—like the audit engine rules and the lead capture strategy—while the AI handled the repetitive plumbing. I also used an LLM to "rubber-duck" my audit engine logic, asking it to find edge cases where my rules might produce incorrect recommendations. This symbiotic relationship between my architectural oversight and the AI's speed allowed me to complete a 7-day project with a level of polish that would typically take much longer.
